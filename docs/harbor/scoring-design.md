# 六个示例的评分设计

中文 | [English](scoring-design.en.md)

这六道题首先是“怎样制作 Harbor Office Task”的教学样例，不是隐藏测试集。输入、gold 和评分器全部公开，适合学习、调试模型和验证评测链路；公开 gold 会降低防作弊能力，因此不能只凭这六题发布正式排行榜。

## 固定分母与硬门槛

每种任务在根目录 `grading/eval_core.py` 中有一张固定评分表。非门槛项的权重固定合计为 1.0，不会因为某段检查提前退出而改变分母。

以下属于硬门槛：

- 交付文件存在；
- 文件能被对应解析器打开；
- XLSX 包含全部必需工作表。

任一门槛失败，reward 直接为 0。门槛通过后，才按业务检查权重累加。`score.json` 会保存每项的 `passed`、`detail`、`weight` 和 `gate`，便于定位差异。

## 提示词与评分器怎样对应

| 示例 | 主要业务要求 | 确定性检查 | 典型负向夹具 |
| --- | --- | --- | --- |
| 数据清洗 | 标准字段、27 条有效费用、风险映射、异常和来源 | 完整产品/费用/风险业务键、数值与日期类型、逐行来源 | 只保留少数正确费用行会失败 |
| 采购对账 | 按订单号汇总入库，再分类数量与金额差异 | 4 张明细的完整主键集合、唯一性、汇总值和代表性金额/数量 | 用重复订单凑够行数会失败 |
| 客服周报 | 周一至周日汇总四周，生成两张 Excel 图表 | 周次、起止日期、记录数、计划量、解决量和完成率逐行关联；图表对象与引用 | 把正确数字散放在任意单元格会失败 |
| 渠道异常 | 去重、排除无效季度、比较全部渠道指标、列出 39 项异常 | 全部 160 条渠道指标汇总、完整异常键、差额/比例、证据与待确认字段 | 只写 6 个抽查值或一条异常会失败 |
| 需求预测 | 不指定算法，但必须做固定历史验证并说明区间 | 36 月源数据、3 个固定验证月、误差算式、MAPE 上限、历史数据驱动边界和原生图表 | 使用 0–5000 等任意大范围会失败 |
| 治理摘要 | 最新登记簿优先、冲突分开、负责人和推断需限定 | 每个事项的编号—状态—日期—来源同一行关联，冲突逐项说明，错误旧口径必须标为旧稿 | 把全部关键词堆在一个段落会失败 |

## 公式怎样检查

`openpyxl(data_only=False)` 只能看到公式文本，不能计算公式。评分环境因此安装 LibreOffice Calc，并按以下顺序检查：

1. 静态扫描公式中的显式错误和明显除零；
2. 将成品复制到临时目录；
3. 用 LibreOffice headless 重新计算并另存；
4. 读取计算后的缓存值，检查 `#REF!`、`#DIV/0!`、`#VALUE!` 等错误。

原文件不会被 LibreOffice 覆盖。含公式但环境无法重新计算时，该项判失败，而不是默认通过。

## 正向与负向回归

根目录 `tests/test_grading_regression.py` 会动态生成六份满足规则的 oracle 成品，并为六类任务各构造至少一种对抗性错误。运行：

```powershell
python -m pytest -q
```

这些夹具只用于测试评分器，不会放入 `workspace.tar.gz`，Agent 也不会在 trial 中看到它们。修改 prompt、gold 或评分逻辑时必须同步修改回归测试。

## 公共实现与任务副本

Harbor 要求每个 task 可独立打包，所以每个任务仍包含 `tests/grading/eval_core.py` 和 `score.py`。仓库以根目录 `grading/` 为唯一维护源，修改后运行：

```powershell
python scripts/sync_grading.py
python scripts/sync_grading.py --check
```

跨平台校验器会拒绝过期副本。这样既保持 Task 自包含，又避免人工维护六份不同版本。
